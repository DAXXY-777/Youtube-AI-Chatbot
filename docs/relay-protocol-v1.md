# Relay Protocol v1 — Draft Contract

**Project:** YouTube AI Chatbot → local-first SaaS  
**Sprint task:** F04  
**Status:** v1 contract ready for initial implementation. Fixture-format tests passed; runtime validation pending. 
**Companion:** `docs/saas-blueprint.md` §5

## 1. Why this exists

Cloudflare Workers/Durable Objects (TypeScript) and the streamer's desktop agent (Python) must agree on exactly what each WebSocket message means. A versioned contract prevents one side from silently interpreting a message differently after an update.

**Scope:** The *internal*, authenticated Worker/Durable Object ↔ desktop relay. This is **not** the public Nightbot HTTP API and does not decide whether Nightbot replies are synchronous or delayed.

## 2. Transport and trust

- The desktop **initiates** a secure outbound WebSocket (`wss://`) to Cloudflare. No inbound PC port is exposed.
- The desktop authenticates with its revocable device credential during the WebSocket upgrade (e.g., a Bearer authorization header). The server authenticates and binds this socket to **one channel** before dispatching jobs.
- Messages are **UTF-8 JSON text frames** containing one JSON object each. Maximum incoming message size: **16,384 UTF-8 bytes**. This is a proposed application limit, to enforce on both sides.
- Protocol field `v` is the integer **1** in every message. Unsupported versions and message types are rejected.
- The Worker/server generates job IDs and resolves the channel from authenticated server-side state. A client-supplied `channel_id` is **not** authorization.
- Never include bearer secrets, Nightbot response callback URLs, provider API keys, or local file paths in relay JSON, logs, or test fixtures.

## 3. Message types

### `ask` — Cloudflare → desktop

```json
{
  "v": 1,
  "type": "ask",
  "id": "64a1a3cb-b71d-4b66-a846-e24df946a067",
  "channel_id": "channel-demo-1",
  "viewer": {
    "id": "youtube:viewer-42",
    "name": "ExampleViewer"
  },
  "prompt": "What game should we play next?",
  "deadline_ms": 1893456000000
}
```

| Field | Contract |
|---|---|
| `v` | Required integer `1` (not a string or boolean). |
| `type` | Required literal `"ask"`. |
| `id` | Required UUID v4 string generated by Cloudflare; unique per accepted request. |
| `channel_id` | Required nonempty string, at most 128 characters; must equal the channel bound to the authenticated socket. |
| `viewer.id` | Required nonempty string, at most 128 characters; an external viewer identifier, **not** an authorization credential. |
| `viewer.name` | Optional string, at most 128 characters; display-only and untrusted. |
| `prompt` | Required trimmed, nonempty string, at most 1,500 characters. |
| `deadline_ms` | Required integer representing an **absolute Unix UTC time in milliseconds**. It must be in the future and no more than 30 seconds from the server's dispatch time. |

**Note:** The example's deadline is deliberately illustrative, *not* an executable live job. Runtime/test harnesses must generate a deadline relative to current time. The existing local Nightbot API permits queries up to 1,500 characters; its prompt builder currently considers up to 700 characters for generation. We will preserve the legacy endpoint and document any intentional cloud-side differences.

### `reply` — desktop → Cloudflare

```json
{
  "v": 1,
  "type": "reply",
  "id": "64a1a3cb-b71d-4b66-a846-e24df946a067",
  "text": "Try a short co-op game so chat can join in!"
}
```

- `v` is integer `1`, `type` is literal `"reply"`, and `id` must exactly match an outstanding `ask` for the same authenticated channel.
- `text` must be a string, trimmed and nonempty, at most **280 characters** after normalization to plain, single-line text. This follows the current app's `MAX_REPLY_CHARACTERS` setting; Cloudflare will also enforce it, even when the desktop already cleans the text.
- A `reply` with an unknown, duplicate, or expired job ID is ignored; it must never generate an extra Nightbot message.

### `job_error` — desktop → Cloudflare

```json
{
  "v": 1,
  "type": "job_error",
  "id": "64a1a3cb-b71d-4b66-a846-e24df946a067",
  "code": "busy"
}
```

- `id` must match an outstanding request for the authenticated channel.
- `code` must be one of: `busy`, `timeout`, `unavailable`, `invalid_request`.
- No raw exception messages, stack traces, secret values, or private inference details are sent to Cloudflare.

## 4. Failure and security rules

1. **Invalid JSON, arrays instead of objects, unknown `type`, unsupported `v`, wrong field types, oversized frames, or missing mandatory fields** must not cause inference. Reject safely; close abusive connections if necessary.
2. **Wrong channel:** never route work based solely on the `channel_id` field; it must match the server-authenticated channel.
3. **Expired job:** do not start work after `deadline_ms`; discard late results. Running inference might not be interruptible, but its late result must not be delivered.
4. **Duplicate ID:** one accepted request may produce at most one delivered response. Do not execute or post a duplicate job twice.
5. **Disconnected device:** Cloudflare applies an explicit timeout/offline response policy rather than holding jobs indefinitely.
6. **No arbitrary execution:** this protocol carries only bounded chat prompts and replies, not commands, filesystem requests, URLs to fetch, or scripts.
7. **No extra fields in v1:** reject unexpected top-level fields to catch accidental contract drift. Any future extensions need an agreed protocol revision.

## 5. Out of scope for F04

- Account signup, D1 tables, OAuth, billing, WebSocket authentication implementation, Durable Objects, and actual inference integration are later tasks.
